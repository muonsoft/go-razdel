# go-razdel contracts (v0.1)

Этот документ фиксирует верхнеуровневые контрактные требования для первой версии библиотеки.

## Scope

- Контракты относятся к публичным API токенизации и сегментации предложений.
- Цель этапа: предсказуемое поведение и совместимость с upstream (`third_party/razdel`) на уровне результатов.
- Документ задает требования, а не внутреннюю реализацию.

## Public API contract

Минимальный публичный API v0.1:

- `Tokenize(text string) []Token`
- `Sentenize(text string) []Sentence`

Ожидаемые структуры результата:

- `Span` содержит `Start` и `End`.
- `Token` и `Sentence` содержат `Span` и `Text`.

Допустимы внутренние изменения реализации, если не нарушены требования ниже.

В линейке 0.x этот API заморожен по смыслу: ломающие изменения идут с bump minor и записью в `CHANGELOG.md`. Go modules не дают compatibility guarantee до v1.0.0.

## Offsets contract (Variant A)

Принят вариант A:

- `Start` и `End` измеряются в UTF-8 байтах исходной строки.
- `Start` inclusive, `End` exclusive.
- Для каждого элемента верно:
  - `0 <= Start <= End <= len(text)`
  - `Text == text[Start:End]`

Это базовая инварианта API. Ее нарушение считается критической ошибкой контракта.

## Behavioral contract

- `Tokenize` и `Sentenize` детерминированы: одинаковый вход -> одинаковый выход.
- Функции не имеют побочных эффектов.
- Для пустой строки возвращается пустой срез результата.
- Поведение должно быть максимально совместимо с upstream.
- Известные расхождения фиксируются в документации с примерами и обоснованием (README и этот файл).

## Compatibility contract with upstream

- Upstream в `third_party/razdel` используется как эталон поведения.
- Каждый реализуемый кусок поведения подтверждается:
  - ссылкой на upstream-тест/пример, или
  - локальным golden-тестом, эквивалентным upstream-кейсу.
- Обновление submodule не выполняется в рамках feature-задач и идет отдельным изменением.

### Offsets vs upstream Python

Upstream строит результат через `find_substrings` и хранит позиции как индексы в Python `str` (срезы и `len` для обычного текста — по **Unicode-кодпоинтам**). Публичный API Go фиксирует `Start`/`End` в **байтах UTF-8** (см. «Offsets contract» выше).

Следствие: для одной и той же строки числа `Start`/`End` в Go и `start`/`stop` в upstream **не обязаны совпадать**, если в строке есть символы, кодируемые в UTF-8 несколькими байтами (кириллица, эмодзи и т.д.). На **чистом ASCII** один символ — один байт и один кодпоинт, поэтому индексы часто равны.

Parity с Python проверять по **последовательности текстов токенов** (`Text`) или с явным пересчётом координат; сравнивать только «сырые» числовые смещения между реализациями без учёта единиц измерения нельзя.

### Токенизация: смайлы и emoji (IGO-47)

Контролируемое отклонение от pinned `razdel.segmenters.tokenize` (upstream [#17](https://github.com/natasha/razdel/issues/17), [#2](https://github.com/natasha/razdel/issues/2)):

| Вход | Python (pinned) | Go |
| --- | --- | --- |
| `:-)` | `:`, `-`, `)` | `:-)` |
| `;-)` / `=-)` | три пунктуационных токена | один токен |
| `✅Сдается` | один токен | `✅`, `Сдается` |
| `счетчики💰` | один токен | `счетчики`, `💰` |

Эвристика emoji близка к Unicode Extended Pictographic, но не является полной таблицей свойств Unicode.

## Error-handling contract

- Публичные функции v0 не возвращают `error`.
- Публичные функции не должны panic на корректном UTF-8 вводе.
- `ByteSpans` (внутренний шаг `Sentenize`) паникует только при программной ошибке: trimmed chunk не найден в исходной строке. Это не режим для пользовательского ввода.
- Поведение на некорректном UTF-8:
  - `Tokenize` не паникует. Каждый невалидный байт становится отдельным атомом `OTHER` (`internal/tokenize/atom.go`). Дальше действуют обычные join-правила: `OTHER` склеивается с соседними `OTHER`/`RU`/`LAT` (кроме emoji-split), поэтому `a\xffb` — **один** токен `"a\xffb"`, а не три.
  - `Sentenize` не паникует; инвариант смещений сохраняется. Parity с Python для невалидного UTF-8 не гарантируется (в Python нет невалидного UTF-8 в `str`).
  - Контракт закреплён тестами `TestContract_invalidUTF8_noPanicAndOffsets` и `TestAtomize_invalidUTF8_*`.

## Performance contract (non-functional)

- Временная сложность: линейная относительно длины входной строки.
- Не допускаются неоправданные аллокации на каждый символ.
- Для каждой крупной итерации желательны benchmark-тесты на:
  - коротких строках;
  - длинных строках;
  - Unicode-heavy текстах;
  - текстах с плотной пунктуацией.

## Contract change policy

- Любое изменение этих контрактов требует отдельного PR/коммита и явного описания миграции.
- Изменение единицы смещений (`byte` -> что-то другое) запрещено в пределах v0/v1 без major-перехода.
